# Project Documentation

Read the affected service skill, continuation, source/contracts and current decisions. Keep README, setup, user journeys, settings, API/architecture, test and release documentation aligned with actual behavior. Distinguish plans, implemented behavior and verified evidence; record unknowns without inventing commands or outcomes.

Evaluate each substantial content update for an illustration that explains a meaningful concept, workflow, state or pitfall. Use the bundled [Ian/Xiaohei skill](../ian-xiaohei-illustrations/SKILL.md) for suitable explanatory imagery under the [project illustration policy](../../docs/illustrations.md). The standing preference already selects this style; generate only useful assets, respecting explicit project requirements and accessible text alternatives. Simple prose, exact code/architecture diagrams and real screenshots remain appropriate when they communicate more faithfully.

Keep image assets in the project, preserve Ian attribution/license, and record placement/spec/QA/paths in the affected service or documentation continuation. Verify image readability, alt text, link targets and responsive rendering when integrating actual images. No generated image may imply real customers, measured behavior or release evidence.

For template changes update [template versioning](../../docs/versioning.md), the changelog and README in the same PR. Generated applications maintain their own version policy separately. Before handoff record actual docs checks, reviewed revision and remaining gaps.
