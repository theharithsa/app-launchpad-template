# GitHub Project tracking

Use one selected GitHub Project for each application. Reuse the existing board when it serves the repository. Otherwise create one under the repository owner with public visibility by default. Choose private when the user requests it. Keep confidential content out of public project descriptions, drafts, fields, and status updates. Record the Project URL, visibility, and repository in the project's delivery documentation.

1. Link the repository to the Project and set it as the default repository for new issues. Configure auto-add for issues and pull requests from the linked repository, including drafts and Dependabot. Import existing issues and pull requests, including historical items. Verify membership against GitHub, since auto-add does not backfill history.
2. Plan milestones around a release or a defined outcome. Give each milestone a scope, acceptance criteria, and a target date when one is known. Give every issue and PR a repository milestone. Use an active triage milestone while scope or timing is open and an active dependency maintenance milestone for unplanned Dependabot PRs.
3. Show the native Milestone field in the Project and save a view grouped by it. Milestones belong to the repository and appear through their assigned issues and PRs. Keep each milestone connected to tracked work and resolve empty milestones that have no planned work. Record relevant milestone and sprint links in the delivery documentation.
4. Plan work in an iteration view. Assign current work to the appropriate sprint, keep unscheduled work visible in the backlog, and carry unfinished work forward during sprint review. Use the milestone for the outcome and the sprint for when the team plans to work on it.
5. Give implementation PRs an explicit issue link and the same milestone where they deliver the same work. Dependabot PRs can serve as the tracked work item. Attach them to the applicable milestone and Project without manufacturing duplicate issues. Keep automated assignments limited to items without a milestone and preserve any existing assignment. Use the template milestone assignment workflow or an equivalent rule. The workflow creates the rolling fallback milestones when it first needs them.
6. Backfill historical items against verified release tags and linked issues. Give closed proposals or work without release evidence a history milestone that preserves their GitHub state. Close milestones when their work is resolved, and keep the relevant release and closure evidence.
7. At setup, sprint review, and release, compare repository issues and PRs against Project membership and milestone assignments. Check open and closed items, dependabot intake, and milestones with zero items. Fix gaps and verify the result. When GitHub access prevents setup, record the exact missing step and verify it once access is restored.

GitHub documents [linking a repository to a Project](https://docs.github.com/en/issues/planning-and-tracking-with-projects/managing-your-project/adding-your-project-to-a-repository), [auto-add](https://docs.github.com/en/issues/planning-and-tracking-with-projects/automating-your-project/adding-items-automatically), [milestones](https://docs.github.com/en/issues/using-labels-and-milestones-to-track-work/about-milestones), and [iteration fields](https://docs.github.com/en/issues/planning-and-tracking-with-projects/understanding-fields/about-iteration-fields).
